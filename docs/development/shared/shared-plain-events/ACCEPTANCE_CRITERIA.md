# Acceptance Criteria — UI-05 Plain events in the shared kit and contracts (CHG-009)

Each criterion is observable and maps to at least one test in TEST_PLAN.md. Criteria may not be changed after implementation starts without a controlled change recorded in DECISIONS.md.

| ID | Story | Type | Criterion (Given / When / Then) | Status |
|---|---|---|---|---|
| AC-01 | US-01 | validation | Given the domain schemas, when an occurrence is parsed, then a task occurrence requires a status of Planned, Done or Overdue, and a plain-event occurrence parses with no status, actor or completion time and is rejected if it carries any of them; one exported helper tells a task occurrence from a plain-event occurrence, and TypeScript narrows on it. | MET |
| AC-02 | US-01 | validation | Given `TaskLogQuerySchema`, when `type` is `all`, `tasks`, `events` or omitted, then it parses; an unknown `type` rejects with a Zod error, as an unknown `status` does. | MET |
| AC-03 | US-01 | happy | Given Margaret's log, when `getTaskLog` is read with `type` `all`, then it returns tasks and plain events newest first with the UI-04 ordering, page size and `total` rules; with `tasks` only task rows; with `events` only plain-event rows, none with a status; any `status` filter returns tasks only (with `type: "events"` it gives `items: []` and `total` 0); `q` combines with both; `total` counts rows after all filters. | MET |
| AC-04 | US-01 | happy | Given a plain-event occurrence key, when `getOccurrence` is called with `type: "all"`, then it returns the occurrence with no status, actor or completion time (assignee kept, PD-055), and without that option it is not found (FD-03); given the reference day, `getTodayOccurrences` with `type: "all"` returns that day's plain events as well as its tasks, oldest first, with client scoping unchanged. | MET |
| AC-05 | US-01 | edge | Given the fixtures, then Margaret has plain-event occurrences in the reference week (26–30 Nov 2026), on the reference day and in the calendar data; every plain-event occurrence belongs to an `automatic` event and every task occurrence to a `manual` event; keys stay unique and equal `eventId:start`; repeated reads return identical data. | MET |
| AC-06 | US-01 | security | Given an existing caller that passes none of the new options, when it calls `getTaskLog` or `getTodayOccurrences`, then it gets exactly the rows it got before this feature (for example Margaret's log still totals 137 rows and the UI-04 design rows, Overdue rows and Recent activity rows are unchanged), and the existing UI-00 and UI-04 tests pass unchanged. | MET |
| AC-07 | US-02 | happy | Given a plain-event occurrence, when the day timeline, week grid or month grid draws it at any block density, then the block uses a neutral token colour, shows no status shape (no check or alert icon), shows the word "Event" wherever the tier shows a status word, and its accessible name contains "Event"; task blocks keep their Planned, Done and Overdue looks unchanged. | NOT MET |
| AC-08 | US-02 | happy | Given a plain-event occurrence, when the event popover opens, then it shows a neutral "Event" label where the status pill goes, with no status icon, no "Done ·" actor text and no completion time. | NOT MET |
| AC-09 | US-02 | happy | Given the lists kit, when a row shows a plain event, then a neutral "Event" label (word visible, no status icon, neutral tokens) appears where a `StatusPill` would go; `StatusPill` and `ActivityRow` behave exactly as before for Planned, Done and Overdue. | NOT MET |
| AC-10 | US-02 | happy | Given the shared switch, when rendered, then it has `role="switch"`, `aria-checked` matching its value, an accessible name from its visible label, a target at least 44px tall, and the words "On" or "Off"; clicking it, or pressing Space or Enter while focused, calls `onChange` with the opposite value; it matches FAM-UI-03's `TaskSwitch` behaviour so that one can be swapped for it. | NOT MET |
| AC-11 | US-02 | happy | Given `EventForm`, when the new hide-Status option is set, then the Status chips are not rendered (absent, not disabled) and the form submits without a status; when it is not set, the form renders and validates exactly as before. | NOT MET |
| AC-12 | US-02 | security | Given the calendar, lists and forms kits with plain events and the switch rendered, when axe runs, then there are no violations; status and event type are never conveyed by colour alone; the new styles use design tokens only (no raw colour values). | NOT MET |
| AC-13 | US-02 | edge | Given the existing kit APIs, when this feature is merged, then every existing kit prop and export keeps its type and behaviour, and the full existing unit, component, integration and e2e suites stay green. | NOT MET |

Types: happy · validation · error · permission · empty · edge · security.
Status values: NOT MET · MET (test passing) · BLOCKED (cite OQ/PD).

AC-06 rests on FD-01 (new options default to the current behaviour), which the human is asked to confirm.
