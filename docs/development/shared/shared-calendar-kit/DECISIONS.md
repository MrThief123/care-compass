## Feature decisions log

### FD-01 — DayTimeline/WeekGrid default `rowPx` raised from 44 to 200; WeekGrid block style changed to match Figma week-view reference
- Date: 2026-09-18
- Context: Human visual QA (screenshots against `/dev-preview-calendar-kit`) found event blocks clipped/unreadable in both grids. A first fix (min-height floors decoupled from duration, `truncate` on WeekGrid labels) removed the clipping but broke duration-proportional sizing (a 20-min and 60-min event rendered the same height) and made WeekGrid labels unreadable (ellipsis cut almost everything, e.g. "09…"). The human then asked for event size to visually track duration (their example: a 30-min event should take up half the space between two adjacent hour marks) and pointed at `docs/design/screens/family-02-calendar.png` / `carer-03-calendar.png` (Notion-calendar-style reference also supplied) for the intended WeekGrid card look. Re-ran `get_metadata` on the Figma file (`DFcLy7U1caCVNlhT6eazF5`) per the human's request to check the file's Components page — still only the `01 · Foundations` page is exposed via MCP (same gap as `docs/design/FIGMA_INDEX.md`, OQ-19), so the exported screen PNGs remain the authoritative reference per that answered OQ.
- Decision:
  - `DayTimeline` and `WeekGrid` both change their `rowPx` prop default from 44 to 200 (only the component defaults — `positionBlocks`' own default and AC-02's explicit-44px-args example are untouched).
  - `DayTimeline` blocks: `style` uses `minHeight: Math.max(height, 88)` (was 104) — now mostly a floor for very short (<25 min) events; most events size from duration alone at the new scale.
  - `WeekGrid` blocks: dropped `truncate`; label text now wraps naturally (2 lines) inside a full `border border-bg-brand` rounded card (was `border-l-2`, left-stripe only) with `minHeight: Math.max(height, 44)`, matching the bordered white-card look in the Figma-exported week-view screens.
- Reason: matches explicit human direction plus the Figma-derived reference screens; duration-proportional sizing was an explicit human requirement, not an assumption.
- Alternatives considered: keeping rowPx=44 and only enlarging card min-heights (rejected — breaks duration-proportionality, which the human explicitly asked to preserve); truncating WeekGrid labels to one line (rejected — human reported it made events unreadable).
- Consequences: `DayTimeline`/`WeekGrid` now render a much taller 07:00–18:00 scroll area (~2200px) at default props; any future screen embedding these components should account for that height (e.g. wrap in a scroll container) rather than expecting the previous ~484px height.
- Human confirmation required: yes — flagged HUMAN REVIEW in PROGRESS.md; awaiting explicit sign-off before PR.
- Test changes caused: `day-timeline.test.tsx` — "positions the 09:00 block 88px from the top of the grid by default" → renamed/updated to assert `top: 400px` (i.e. `(9-7)*200`), reflecting the new default `rowPx`. Flagged for review, yes.

### FD-02 — Superseded FD-01's scale: `rowPx` reduced 200→72, `DayTimeline` block redesigned to a single-line row, to fit a whole day/week on one page without scrolling
- Date: 2026-09-18
- Context: Human viewed round 2's result (`rowPx=200`) and reported it "extremely stretched out" and asked that the kit "fit cleanly and size up into a single page view without scrolling," explicitly directing a re-check of the Figma MCP and `docs/design/screens` for how the components are used **within actual screens** (not just the Components page, which per OQ-19/FIGMA_INDEX.md is still unreachable via MCP — re-confirmed unreachable in round 2, not re-checked again this round since nothing indicated the gap had changed). Read `docs/design/screens/family-01-home.png` (Family Home "Today" panel — the actual reference for `DayTimeline`, not previously consulted; round 2 only used the two Calendar-screen WeekGrid references) and re-examined `family-02-calendar.png`/`carer-03-calendar.png` for `WeekGrid`. Measured the reference: the 07:00–18:00 hour rail spans ~780px of actual design canvas (~66–71px per hour), and the whole calendar (plus header and content below it, e.g. Tasks/Log/Budget) fits in one ungenerated-scroll screen. Critically, `DayTimeline`'s reference layout is a **single horizontal line per event** (title, assignee, duration inline; status pill right-aligned) — not the stacked 4-line vertical card round 1/round 2 built — which is what lets it stay legible at a compact row height while still tracking duration (a 1-hour event in the reference occupies exactly one hour-row).
- Decision:
  - `DayTimeline` and `WeekGrid` both change their `rowPx` prop default from 200 to 72 (≈ the measured Figma reference scale; also keeps the literal "30-min event = half an hour-row" rule from FD-01, since 72/2 = 36).
  - `DayTimeline` block markup rebuilt from a vertical `flex-col` card to a horizontal `flex items-center justify-between` row: title, assignee and duration inline on the left (title `truncate`d, the rest `shrink-0`), `StatusPill` right-aligned — matching `docs/design/screens/family-01-home.png`'s "Today" panel. `minHeight` floor lowered from `Math.max(height, 88)` to `Math.max(height, 40)` since a single line + pill no longer needs 4 stacked lines of vertical room.
  - `WeekGrid`'s card markup (bordered card, 2-line wrapping `"HH:mm Title"` text) is unchanged from FD-01 — only its `rowPx` default changes; its existing `Math.max(height, 44)` floor already fit this smaller scale without further adjustment.
  - No change to `positionBlocks`' own default or AC-02's explicit-44px-argument example.
- Reason: direct human instruction to match the design references' actual on-screen scale and to eliminate full-page scrolling, which `rowPx=200` (FD-01) did not achieve — FD-01 optimized only for duration-proportionality in isolation without checking the reference screens' absolute scale or their (non-stacked-card) event layout.
- Alternatives considered: keeping `rowPx=200` and wrapping the hour grid in an internal `overflow-y-auto` scroll container (rejected — the reference screens show no internal scroll either; the human's request and the reference both point to a smaller absolute scale, not a scroll region); shrinking only `WeekGrid` and leaving `DayTimeline` at 200 (rejected — human's report covered "these two grids," and the Family Home reference makes clear `DayTimeline` is meant to be compact too).
- Consequences: `DayTimeline`/`WeekGrid` now render an ~800px-tall 07:00–18:00 area at default props (down from ~2200px), consistent with the Figma-exported screens fitting on one page. `DayTimeline`'s DOM structure changed (vertical card → horizontal row) but no test assertion needed to change for that, since `day-timeline.test.tsx` only asserts text presence via `within(...).getByText(...)`, not layout/position.
- Human confirmation required: yes — flagged HUMAN REVIEW in PROGRESS.md; awaiting explicit sign-off (this supersedes FD-01's still-unreviewed sign-off request — human has not yet approved either FD-01 or FD-02's test change).
- Test changes caused: `day-timeline.test.tsx` — "positions the 09:00 block 400px from the top of the grid by default" (FD-01's value) → updated again to assert `top: 144px` (i.e. `(9-7)*72`), reflecting the new default `rowPx`. Flagged for review, yes.

### FD-03 — Figma Components page became reachable; supersedes FD-01/FD-02's screenshot-derived `rowPx`/card guesses, rebuilds `MonthGrid` to match the actual Calendar screens, and fixes two cross-lane token bugs it surfaced
- Date: 2026-09-18
- Context: Human gave a direct node URL (`.../design/DFcLy7U1caCVNlhT6eazF5?node-id=1-60`) into the file's `02 · Components` canvas. Unlike a bare `get_metadata` call (still only enumerates `01 · Foundations`, per OQ-19/FIGMA_INDEX.md — this gap is unchanged), fetching that specific node ID works and exposes `Timeline hour row`, `Event block`, `Calendar event chip`, `Building Blocks/Date cell` and `Status pill` with authoritative tokens and usage notes — the first time this feature has had real Components-page data rather than eyeballing exported screen PNGs. Human also asked for `WeekGrid`/`MonthGrid` to be rebuilt against `docs/design/screens/carer-03-calendar.png` and three pasted Family Calendar (Month ×2, Day) screen images (not yet exported into the repo).
- Decision:
  - **`rowPx` reverted 72 → 44** for `DayTimeline` and `WeekGrid`. `Timeline hour row`'s node description states the band is `44px` (`--size-row-calendar`), which also matches `positionBlocks`' own untouched default and AC-02's explicit 44px-row example (tops 88px/198px) — FD-02's `72` was a screenshot-pixel estimate made before the Components page was reachable and is superseded.
  - **`DayTimeline` block background** `bg-bg-brand-pale` → `bg-bg-inset`, stripe changed from a `border-l-2` to a dedicated `w-1` block + `rounded-r-inset` (right corners only), body padding/gaps set to `px-3 py-2 gap-3`, assignee/duration text size `text-body-small` → `text-body-secondary` (12px) — all per the `Event block` node spec. FD-02's `bg-brand-pale` was picked against a lower-fidelity reference; the new Family Calendar (Day) screen image and the Figma token agree on the paler `bg-inset`.
  - **`WeekGrid` today column**: background wash now applied to the header cell *and* the full-height day column (was header-only), using `bg-bg-inset` (was `bg-bg-brand-pale` on the header only) — `carer-03-calendar.png` shows one continuous tint down the whole MON column, not just behind the header text. Hour rows in both the gutter and every day column now draw a `border-t border-border-subtle` hairline, matching `Timeline hour row`'s drawn grid line (previously no horizontal lines at all).
  - **`WeekGrid` event card**: kept the full-border, all-corner-rounded white card (this matches `carer-03-calendar.png` exactly, unlike the `Calendar event chip` node's stripe+right-rounded-only style — screen reference wins over the generic symbol here per the human's explicit per-view references), but now splits `"HH:mm"` and the title onto two separate lines/text styles (`text-body-secondary` then `text-body-small`) instead of one concatenated string, and drops manual truncation logic in favour of CSS `truncate` on the title line — matching the two-line card in the reference image pixel-for-pixel.
  - **`MonthGrid` rebuilt from a small dot-indicator picker grid (duplicate of `DatePickerGrid`) into a full month calendar**: takes `occurrences: Occurrence[]` (breaking change from `datesWithEvents: LocalDate[]`) plus a `labelFormat` prop mirroring `WeekGrid`'s; each cell shows a day-number badge (filled `bg-bg-brand-deep` circle when selected, `border-border-brand` outline when today-but-not-selected, per `Building Blocks/Date cell`'s two distinct states) and a stacked list of flat `bg-bg-brand-pale`/`text-text-brand` event chips (`"HH:mm Title"`, truncated). This matches the pasted Family/Carer Calendar (Month) screen images, which use a flat single-line pill per event — not the bordered/striped `Calendar event chip` node (that symbol is a two-line, fixed-40px-body component that doesn't reflow to the screens' compact one-line-per-event list; the screens win, per the human's explicit references). Out-of-month cells (numbers and their chips) render at `opacity-50`. No overflow/"+N more" affordance was built — not shown in either reference image and not in PRD scope; noted under Assumptions.
  - **Cross-lane token fixes surfaced by the `Status pill` and `Event block` node docs** (component is `src/components/shared/status-pill.tsx`, owned by F0-14 — already `MERGED TO DEV` — not this feature's own files, but needed for `DayTimeline`'s status pill to render as documented): `status="planned"` border `border-border-default` → `border-bg-muted` (Figma `border/muted` token, `#8db8c8`, already mirrored in `tokens.css` as `--color-bg-muted`) and background `bg-transparent` → `bg-bg-surface` (opaque white — the node description explicitly warns transparent doesn't stay legible inside an `Event block`'s tinted ground); `status="overdue"` ink `text-text-alert` → `text-text-alert-strong` (node description: `text-alert` only reaches 4.42:1 contrast on `bg-alert`, `text-alert-strong` reaches 7.0:1).
- Reason: the Components page is now reachable for the calendar-relevant nodes and gives exact tokens/measurements superseding FD-01/FD-02's screenshot-pixel estimates; the pasted screen images are the most direct reference for `MonthGrid`, which had no prior visual QA round at all (only unit-tested against the small-picker-grid AC wording, never checked against an actual Calendar screen).
- Alternatives considered: keeping `MonthGrid` as the small dot-picker and building a separate new component for the big calendar (rejected — PRD's UI/UX Requirements line explicitly says match "... Family Calendar, Carer Calendar ... frames", and `DatePickerGrid` already covers the small-picker case, so a second component would duplicate it); using the literal `Calendar event chip` node markup for `WeekGrid`/`MonthGrid` verbatim (rejected — its fixed two-line 40px body doesn't match either screen's actual chip proportions; screens were the human's stated source of truth for these two views).
- Consequences: `MonthGrid`'s public prop contract changed (`datesWithEvents` removed, `occurrences`/`labelFormat` added) — no other code consumes it yet (FAM-UI-02/CAR-UI-03 are NOT STARTED), so this is a same-session breaking change, not a cross-feature one. `status-pill.tsx` (F0-14, lane S, already merged) picked up two class changes outside this feature's own file list — flagged below and in PROGRESS.md rather than silently bundled.
- Human confirmation required: yes — flagged HUMAN REVIEW in PROGRESS.md; awaiting explicit sign-off (this supersedes FD-01 and FD-02's still-unreviewed rowPx/test changes with a Figma-token-backed value that also happens to restore FD-01's *original* pre-guess number).
- Test changes caused:
  - `day-timeline.test.tsx` — "positions the 09:00 block 144px..." (FD-02) → "...88px..." (`(9-7)*44`), reflecting the reverted default `rowPx`. Flagged for review, yes.
  - `week-grid.test.tsx` — `within(thursday).getByText("09:30 Weekly weigh-in")` (one node) → two assertions, `getByText("09:30")` and `getByText("Weekly weigh-in")` (two nodes), reflecting the new two-line card markup. Flagged for review, yes.
  - `month-grid.test.tsx` — fully rewritten from `datesWithEvents`/dot-indicator assertions to `occurrences`/chip-text assertions, tracking the prop-contract change; added a `labelFormat` test mirroring `WeekGrid`'s. Flagged for review, yes (contract change, not just a value change).

### FD-04 — DayTimeline/WeekGrid block height now tracks duration exactly; WeekGrid card rebuilt to a single line so it degrades gracefully at short durations
- Date: 2026-09-18
- Context: Human asked directly (not via Figma/screenshot QA) that block length visually track event duration — "an hour event should take up 1 block in the grid, half an hour takes half, etc." Both components already computed a duration-proportional `height` via `positionBlocks` (AC-02), but each one discarded it behind a `minHeight` floor (`DayTimeline` 40px, `WeekGrid` 44px, both from FD-01/FD-02/FD-03 legibility fixes) — at the current `rowPx=44` default, that floor made any event ≤ ~55 min render at nearly the same height as a full 60-min event, defeating proportionality. Switching to the raw computed `height` (fixed, not a floor) exposed a second, pre-existing problem: `WeekGrid`'s event card (FD-01/FD-03's bordered, two-line "HH:mm" + title stacked card) needs ~32–40px to render both lines without clipping, so at real short-event heights (11px for a 15-min event, 22px for 30-min) the border/radius rendered as a distorted pill with the title line invisible and the time line partly overflowing the box — confirmed via a Playwright screenshot against `/dev-preview-calendar-kit`, not caught by any existing test (no test asserted on card height or overflow).
- Decision:
  - `DayTimeline` block: `style` `minHeight: Math.max(height, 40)` → `height` (exact, no floor).
  - `WeekGrid` block: `style` `minHeight: Math.max(height, 44)` → `height` (exact, no floor); markup rebuilt from a bordered, `rounded-inset`, `flex-col` two-line card to a single-line `flex items-center` row — `border` (all sides) → `border-l-2` stripe (matching `DayTimeline`'s own left-stripe treatment), `rounded-inset` → `rounded-r-inset`, `py-1` padding dropped (vertical centring via `items-center` instead), time and title now sit side by side (`shrink-0` time, `truncate` title) instead of stacked. No `positionBlocks`/AC-02 change; `rowPx` default unchanged from FD-03 (44).
- Reason: direct, unambiguous human instruction that duration should determine block size, at the pixel-exact ratio AC-02 already specifies for the pure helper — the two component-level floors were the only things stopping that from showing on screen. The `WeekGrid` card redesign is a consequence, not a separate request: keeping the two-line bordered card would satisfy "duration dictates height" in spec but render broken/illegible below ~40px, which fails the same request in practice.
- Alternatives considered: keeping a smaller floor (e.g. 16–20px) instead of removing it entirely (rejected — the human's example was exact proportionality, "half an hour takes half," which a floor breaks for every event shorter than the floor implies); keeping `WeekGrid`'s two-line card and just shrinking its padding/font further (rejected — even at zero padding two lines of any legible type need >20px, which is still taller than several real short-duration events in the fixture data, e.g. the 15-min/20-min events already in `/dev-preview-calendar-kit`); this is a known accessibility tension worth flagging rather than silently resolving — `DayTimeline`'s block is a `<button>` with an `onSelect` handler, and ARCHITECTURE.md/CLAUDE.md's 44×44px touch-target rule would be violated by any event under ~55 minutes at this scale. Not resolved here (would need a hit-area-vs-visual-size split or a rethink of whether sub-hour events should be individually clickable in this view) — flagging for human review rather than guessing.
- Consequences: both grids now render short events as visually thin slivers (a 15-min event is 11px tall) — expected/intended per the human's request, but very little text fits inside a `DayTimeline` block under ~20px (still one truncating line, same as before, just less width for it); `WeekGrid`'s card visual style changed from a bordered two-line card back to a stripe+single-line row (closer to FD-01's original style than FD-03's Figma-node-matched one) to survive the smaller sizes — flagging since FD-03's card style was matched pixel-for-pixel against `carer-03-calendar.png`, and this changes it again.
- Human confirmation required: yes — flagged HUMAN REVIEW in PROGRESS.md; awaiting explicit sign-off, including on the unresolved touch-target question above.
- Test changes caused: none removed; two tests added (`day-timeline.test.tsx`, `week-grid.test.tsx`) asserting exact `height` in px for events shorter than an hour, added before the fix (confirmed failing against the pre-fix floor-based heights, then passing after). No existing assertion changed.

### FD-05 — All three views rebuilt on four shared primitives: full-day scroll, overlap columns, density tiers and a click-to-expand popover; supersedes FD-04's "thin slivers" outcome and resolves its touch-target question
- Date: 2026-09-18
- Context: Human visual QA of `/dev-preview-calendar-kit` against three Notion Calendar reference screenshots (day, week, month), with per-view direction: **Day** — text cut off, borders inaccurate, blocks should be flex boxes that resize with the window, information should stay viewable at any duration, over-packed small events should hide detail and reveal it on click, scrollable 00:00–23:59 defaulting to 07:00–18:00, nothing cut off "even in the corner designs", "treat it as an exact working calendar system". **Week** — cells too tightly spaced to see events at all, blocks should resize dynamically, scrollable across the whole day. **Month** — grid so small only dates and times are visible, "useless from a usability perspective"; start time *and* event name must be visible for the majority of events. FD-04 had made block height exactly proportional to duration with no floor, which produced the unreadable slivers this round was called to fix; its own "Alternatives considered" flagged the resulting 44×44px touch-target violation as unresolved.
- Decision:
  - **Four new shared primitives**, so the three views share one implementation of each concern rather than three: `src/lib/dates/layout-blocks.ts` (`layoutBlocks` — overlap clustering into side-by-side columns, plus a `minHeightPx` floor that keeps `durationHeight` alongside the clamped `height`); `block-density.ts` (`blockDensity(px)` → `compact` | `regular` | `full`); `time-grid-scroller.tsx` (the full-day scrolling hour canvas, gutter, gridlines and open-on-focus-hour behaviour shared by Day and Week); `event-popover.tsx` (portalled, `fixed` detail card — portalled because an in-flow card is clipped by the scroll container). `status-cue.ts` was extracted afterwards so all three views share one status treatment.
  - **Readable minimum restored, but only as a floor.** FD-04 removed the floor entirely to get proportionality; this reinstates a 22px floor *and* keeps proportionality above it, which is what the human actually asked for in both rounds — the floor now resolves FD-04's open touch-target question by making 22px the smallest a block is ever rendered and clickable, with the popover carrying anything that no longer fits.
  - **Density tiers replace "fit everything into every block".** Thresholds are measured against the rendered type ramp, not round numbers: `regular` ≥ 40px (title 16 + range 16 + 8 padding), `full` ≥ 72px (adds a 26px status row + 4px separation). 56 and 64 were both tried for `full` and both clipped their own last line in the browser.
  - **Status is never hidden behind a click.** The `full` tier renders `StatusPill`; `compact` and `regular` render a coloured left bar plus an icon for `done`/`overdue` plus an `sr-only` status word. An overdue medication must look overdue at a glance in a care calendar, so status is the one thing the density tiers never drop.
  - **Month**: cells are flex rows with a 120px minimum; chips render the start time (muted, `tabular-nums`, `shrink-0`) beside the title (primary, `truncate`, `min-w-0`) so only the title ever truncates; `maxChipsPerDay` (default 4) caps the rows with an `N more` summary, floored so at least one chip always stays visible.
  - **Week**: the compact tier drops its trailing time below an 8rem container width (Tailwind v4 container query) so a narrow overlap column spends its space on the event name rather than on a timestamp the popover repeats.
- Reason: direct human direction per view, with the reference screenshots as the visual target. The shared-primitive split was chosen over three per-view implementations because all three views needed the same four behaviours, and CLAUDE.md §7 requires one pattern per problem.
- Alternatives considered: raising `rowPx` so short events grow taller (rejected — FD-01/FD-02 already tried 200 and 72 and the human rejected both as over-stretched; 44 is the Figma `Timeline hour row` token per FD-03); letting each view own its own scroll/overlap/density logic (rejected — three copies of the same arithmetic); keeping FD-04's floor-free proportionality and shrinking type instead (rejected — the ramp bottoms out at 12px `text-body-secondary` per UI-§5.1, well above what an 11px block can show).
- Consequences: `DayTimeline`/`WeekGrid` gain `dayStartHour`/`dayEndHour`; their existing `startHour`/`endHour` now mean the *opening focus window* rather than the grid extent — a silent meaning change for any future caller that passed them, though none exists yet. `WeekGrid` gains `onSelectOccurrence`, `MonthGrid` gains `maxChipsPerDay`. Block height is proportional to duration above 22px and floored below it, so FD-04's exact-proportionality property now holds only above the floor.
- Human confirmation required: yes — flagged HUMAN REVIEW in PROGRESS.md, together with the still-unsigned-off FD-01–FD-04.
- Test changes caused (all flagged **HUMAN REVIEW: test expectation changed**):
  - `day-timeline.test.tsx` — "renders an hour gutter from 07:00 to 18:00" renamed to "renders the whole day so any hour can be scrolled to"; before, it asserted `06:00`/`19:00` are absent, after it asserts `00:00`–`23:00` are all present. Reason: the grid is now the whole day and 07:00–18:00 is only the opening scroll window.
  - `day-timeline.test.tsx` — "positions the 09:00 block 88px from the top of the grid" → 396px. Reason: blocks are positioned from `dayStartHour` (00:00), not from the focus hour.
  - `day-timeline.test.tsx` — "renders each occurrence's title, assignee, duration and status pill" **deleted**, replaced by three per-tier tests. Reason: that expectation — four items crammed into a 22px block — is the defect this round was called to fix. `formatDuration` is no longer rendered on a block at all; it now appears only in `EventPopover`, where the replacement tests assert it. **Behaviour change and an assertion moved, not just a value.**
  - `week-grid.test.tsx` — "[AC-02] sizes a block's height in proportion to its duration": the 15-minute/11px fixture became 60-minute/44px and 120-minute/88px fixtures, and the lookup moved from `closest("[style]")` to a `data-testid`. Reason: 11px is no longer the intended height for a 15-minute event; proportionality is still asserted above the floor, and the floor has its own test.
  - `month-grid.test.tsx` — `getByText("09:00 Morning medication")` (one node) → separate `09:00` and `Morning medication` assertions. Reason: the chip now renders time and title as separate elements so only the title truncates.
  - `time-grid-scroller.test.tsx`, `block-density.test.ts` — new primitives' own tests, adjusted twice as the density thresholds and the 8px hour-label bleed were measured in the browser. No pre-existing assertion involved.
- AC status: AC-01 – AC-06 all still MET; AC-02's `positionBlocks` contract (tops 88/198, heights 44/66 at 44px rows) is untouched, and AC-03's "09:30 Weekly weigh-in under THU 3" still holds with the time and title as separate nodes.
