## Feature decisions log

### FD-01 — Scope, from CHG-025 and the start-of-feature answers
- Date: 2026-09-30
- Context: PRD and ACs (2026-09-17) still describe Family document notifications and a trigger on insert only. CHG-025 dropped Family notifications and set the triggers to shift assigned, changed and cancelled.
- Decision: only shift notifications, all `source = 'admin'`. `carer_notifications.source` keeps the `'admin'|'family'` check so a later feature can add Family without a migration, but nothing writes `'family'`. No `client_id`-based fan-out, no document trigger. The 'Family' chip stays in `NotificationRow` and is unused. ACs rewritten to 12 (below); the four originals are superseded (AC-02 family document and AC-03 permission become AC-05).
- Reason: CHG-025; F0-13 (documents) is a dependency only for history and is no longer a trigger source.

### FD-02 — Which shift changes notify
- Date: 2026-09-30
- Decision (human, 2026-09-30):
  - Shift inserted (not cancelled) → the carer gets `shift_assigned`.
  - `starts_at` or `ends_at` changes on a non-cancelled shift → `shift_changed` to that carer.
  - `carer_id` changes on a non-cancelled shift → the old carer gets `shift_cancelled`, the new carer gets `shift_assigned`.
  - `cancelled_at` goes from null to set → `shift_cancelled`. Un-cancelling is not notified. Updating any other column notifies nobody. A shift already cancelled notifies nobody on further updates.
  - A bulk cancel (for example `transfer_client_organisation` cancelling future shifts) notifies every affected carer through the same trigger.
- Reason: the carer's own shift list changes in each of those cases.

### FD-03 — Message text is generated in the database, with the client's full name
- Date: 2026-09-30
- Decision (human, 2026-09-30): messages carry the client's **full name**, per CHG-032, generated by the SECURITY DEFINER trigger function in `Australia/Melbourne` time, from the shift row and the client row:
  - `New shift assigned: Tuesday 1 Dec, 09:00–11:00 (Margaret Doyle).`
  - `Shift changed: Wednesday 2 Dec now 13:00–17:00 (Margaret Doyle).`
  - `Shift cancelled: Friday 4 Dec, 08:00–12:00 (Margaret Doyle).`
  Date is `FMDay FMDD Mon` (no leading zero, English), times `HH24:MI` with an en dash. End time is shown as a time only; a shift that crosses midnight shows the end clock time without a date (accepted, shifts are not expected to).
- Test changes caused: CAR-UI-01 expectations and `CARER_NOTIFICATIONS` fixture text `(Margaret)` → `(Margaret Doyle)` in `src/mocks/fixtures.ts`, `src/server/notifications/queries.test.ts`, `src/features/carer-home/carer-home.test.tsx`. **HUMAN REVIEW: test expectation changed** (recorded in PROGRESS.md; flag in the PR). `carer-patients.test.tsx` and `tenancy_rls.test.sql` also contain `(Margaret)`; check whether they concern these messages and leave them alone if not.
- This is the CAR-02 share of the CHG-032 sweep; the rest of the sweep stays unscheduled.

### FD-04 — Read state and the bell
- Date: 2026-09-30
- Decision (human, 2026-09-30): `read_at` null = unread. The bell shows the unread count (badge, hidden at 0, `9+` above 9; accessible name `Notifications, N unread`, or `Notifications` at 0). Clicking it:
  - on `/carer/home`: scrolls to the Notifications card, moves focus to it, and marks **all** the carer's notifications read;
  - anywhere else in the carer app: navigates to `/carer/home#carer-home-notifications`, then does the same on arrival.
  Unread rows show a small dot with the accessible text 'Unread' (status never by colour alone). There is no per-row control. Read rows stay listed (no deletion or expiry in this feature; the card shows the newest 50).
- Mock mode: `markCarerNotificationsRead` flips `read` on an in-memory copy so the dev preview behaves; the fixture module is not rewritten.

### FD-06 — Table, RLS and contract shape
- Date: 2026-09-30
- Decision: one migration made with `supabase migration new carer_notifications`:
  - `carer_notifications(id uuid pk, recipient_id uuid → profiles on delete cascade, source text check in ('admin','family'), kind text check in ('shift_assigned','shift_changed','shift_cancelled'), message text, client_id uuid → clients on delete cascade, shift_id uuid → shifts on delete set null, created_at timestamptz default now(), read_at timestamptz)`, index on `(recipient_id, created_at desc)`, RLS enabled in the same migration.
  - Policies: select where `recipient_id = auth.uid()`. No insert or delete policy for `authenticated`. Update allowed only on the recipient's own rows and only the `read_at` column (`revoke update`, `grant update (read_at)`).
  - Trigger function `notify_carer_of_shift_change()` SECURITY DEFINER, `set search_path = public`, `after insert or update on shifts`.
  - Contract additions in `src/server/notifications/`: `getCarerNotifications(carerId)` gets its Supabase branch (own rows, newest first, limit 50, `read = read_at is not null`); new `getCarerUnreadCount(carerId)`; new `actions.ts` with `markCarerNotificationsRead()` (Zod-free, no input; result shape `{ok:true}|{ok:false,error}` as `src/server/clients/actions.ts`). The action updates `read_at = now()` where `recipient_id = auth.uid() and read_at is null`.
  - `CarerNotification` type unchanged.
  - Client data: `client_id` is stored for future use; a carer whose read access to the client ended (PD-041) still sees the message text, which is all the carer needs and names only what the assigned shift already named.
- Retention: none in this feature.
